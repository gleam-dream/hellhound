# Pending logins live in sealed browser cookies

<a id="adr-0026"></a>

- **Decision:** `begin_login` stores nothing on the server. It seals the pending login (state, nonce, PKCE verifier, redirect URI, `max_age`, issuer, client id and expiry) with the client's sealing key ring into a cookie, and `complete_login` opens that cookie. The cookie is named `__Secure-hellhound_login_` plus 64 bits of the state's SHA-256 digest, is `Secure`, `HttpOnly`, `SameSite=Lax` (`None` for form-post callbacks, which arrive as a cross-site POST), is scoped to the path of the login's redirect URI, and lives for the login lifetime. `callback_response` expires it. The server-side login store, `config.with_transaction_store`, `config.with_max_pending_logins`, the browser-binding cookie and the `request` argument of `begin_login` are removed, with no compatibility path.
- **Need:** every `begin_login` call occupied a slot in a bounded store for twice the login lifetime. With the defaults (100 000 records, 10 minutes) about 84 anonymous requests per second kept the store full, and every user's login then failed with `TooManyPendingLogins`. A durable store had no bound, so the same requests grew a table without limit. Any per-browser cap or eviction keeps shared state that an attacker can still fill or churn. The owner ruled to remove the shared state.
- **Supersedes:** the "pending login" half of [ADR 0004](0004-sealed-cas-custody.md)'s decision that one store serves pending login and custody records, its rejection of stateless encrypted cookies, and its 100 000 pending-login capacity. The store now holds custody records only. ADR 0013's guarded write (`AtVersionBefore`) is no longer used by login; the store contract keeps it unchanged.
- **Binding to the client:** the sealing additional data binds the record kind and the state, so a cookie presented under another login's name does not open. The sealed material names the issuer and client id; a callback reaching a client with another issuer or client id that shares the sealing key is refused as `ForeignLogin` before any token request. This closes the gap where two tenants' clients sharing a store and key accepted each other's pending logins, and it leaves the RFC 9207 `iss` check unchanged.
- **Single use:** Hellhound no longer refuses a second callback that carries the same cookie and code. Single use rests on the provider: RFC 6749 §4.1.2 requires a provider to accept an authorization code once, and the code exchange needs the PKCE verifier, which exists only in that browser's cookie. Consequences:
  - A browser that received `callback_response` holds no cookie, so its reload is refused locally with `LoginCookieMissing`.
  - Concurrent duplicates of one callback each send a token request; one can succeed and the rest get the provider's refusal (`ExchangeRejected(InvalidGrant)`). RFC 6749 §4.1.2 asks the provider to revoke the tokens already issued for a reused code, so a duplicated callback can end the first session.
  - A copied cookie and callback URL replayed before the lifetime ends reach the provider, which refuses the used code. Copying them needs the browser's `HttpOnly` cookie, which is already enough to take over the login.
  - `LoginReplayed`, `LoginChanged`, `TransactionStoreUnavailable`, `LoginRecordUnreadable`, `LoginStoreUnavailable` and `TooManyPendingLogins` are removed.
- **Missing, expired or tampered cookies:** each is a typed refusal that sends nothing to the provider. No cookie for the callback's state (another browser, a cleared cookie, an elapsed `Max-Age`) is `CallbackRejected(LoginCookieMissing)`. A cookie that does not open (altered, sealed for another state, or under a key the client does not hold, such as an ephemeral key from before a restart) is `CallbackRejected(LoginCookieInvalid)`. A sealed expiry in the past is `LoginExpired`. All `CallbackRejected` variants map to `RejectRequest`; `LoginExpired` maps to `Reauthenticate`.
- **Cookie size:** the cookie value is the base64url form of about 250 bytes of fixed material plus the issuer, client id and redirect URI, with 37 bytes of sealing overhead. Measured: 383 characters with empty issuer, client id and redirect URI; 470 for a typical configuration; 3 114 at the 2 KiB limit below. Browsers keep 4 KiB per cookie, so configuration validation refuses a relying party whose issuer, client id and longest redirect URI exceed 2 KiB together (`LoginCookieTooLarge`). The path scope keeps the cookies off every request except the callback. A browser that starts many logins without finishing them sends one cookie per pending login to the callback until each expires; ten pending logins of a typical configuration add about 5 KiB to that request's headers, which a server with an 8 KiB header limit still accepts.
- **Nodes and keys:** without `config.with_sealing_key` each client seals with a random in-memory key, so a callback must reach the node that started the login, before a restart; this matches the former in-memory store. With one sealing key on every node, any node completes any login, which needed a durable transaction store before. Rotating the key with `with_previous_sealing_keys` keeps pending logins valid.
- **Cookie scope trade-off:** a `__Host-` name would forbid a `Domain` attribute and stop a sibling subdomain from planting a cookie, but it requires `Path=/`, which sends every pending login's cookie with every request to the host. The owner asked for path scoping, so the cookie uses the `__Secure-` prefix. A host that shares its registrable domain with an untrusted subdomain can then receive a cookie that subdomain set for an attacker's own pending login, which enables login CSRF against that host's callback. The former `__Host-` binding cookie did not have this exposure. Applications with untrusted sibling subdomains should serve the callback from a host whose parent domain they control.
- **Rejected alternatives:**
  - Keep the store and cap pending logins per binding cookie: an attacker mints a new binding per request, so the shared capacity still fills.
  - Keep the store and retain pending records for one lifetime only: it halves the flood rate needed, and does not remove it.
  - Document a rate limit as the application's duty: it leaves a lockout one missing proxy rule away.
  - One cookie for all pending logins of a browser: parallel tabs overwrite each other.
  - Bind issuer and client id only through the sealing additional data: a foreign login would read as tampering, without the typed `ForeignLogin` refusal that tells an operator two clients share a key.
- **Provenance:** `test/hellhound_sealed_login_test.gleam` covers tampered, forged and renamed cookies, a callback without its cookie, foreign issuer and client id, expiry, two parallel logins, 5 000 login starts followed by another login, and the cookie attributes and clearing.
