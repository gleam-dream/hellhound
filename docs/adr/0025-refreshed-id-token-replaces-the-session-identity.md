# A refreshed ID token replaces the session identity, and the session says where its identity came from

<a id="adr-0025"></a>

- **Decision:** when a refresh response carries an ID token that passes the continuity checks (issuer, subject, audience, authorized party, original nonce, original `auth_time`), its verified payload replaces the sealed identity in the same publication that replaces the token material. `session_identity` therefore returns the refreshed claims after `refresh` or `access_token`, and every later restore of that session agrees. A new public `IdentityOrigin` (`LoginIdentity`, `RefreshedIdentity`, `RetainedIdentity`) and `session_identity_origin(session)` tell the caller whether the identity at the session's current revision came from login, from the ID token of the refresh that published it, or was retained because that refresh returned no ID token.
- **Need:** a consumer that re-checks authorization claims on refresh could not see them. Custody sealed the refreshed ID token as the logout hint but kept the login-time claims, and no public function exposed the refreshed ones, so a role removed at the provider stayed visible until the next login.
- **Shape:** the change is additive. `Access` and its fields are unchanged, because adding a field to a public record breaks every caller that constructs or positionally matches it. The origin lives on `Session`, not on the refresh result, so it is the same for the request that dispatched the refresh, a request that joined it, a stale session value that read the newer revision, and `recover_refresh`. The ID token and its identity are replaced as one value inside custody, so the sealed hint and the sealed claims cannot disagree.
- **Stored records:** the origin is sealed with the record. A record written before this change has no origin and opens as `LoginIdentity`, which is accurate: those versions never replaced the login identity.
- **Unchanged:** refresh never creates a new authentication event. Continuity checks, including refusing a changed `auth_time`, and quarantine on a rejected response are as in [ADR 0005](0005-refresh-uncertainty.md). The stable identity key stays the login's `(issuer, subject)`. Reading a claim still grants nothing; the application decides what a changed claim means.
- **Alternatives:** a new `refresh` variant returning the refreshed identity would leave `access_token`'s margin refresh, joined refreshes and later restores reading stale claims. Changing the return type of `refresh` and `access_token` would break every consumer for a need the session can carry.
