# Fix the local issuer's port and keep a loopback-constrained root for a local run

<a id="adr-0024"></a>

- **Decision:** the public local issuer gains `with_port` and `with_trust_anchor(directory)`, and a new `start` that returns a typed `StartError` (`InvalidPort`, `PortInUse`, `TrustAnchorFailed(directory, TrustAnchorError)`, `StartFailed`). With an anchor directory, the first start writes a P-256 root and its key there; later starts load and reuse the root and sign a fresh leaf for `localhost` and 127.0.0.1 per start. `replace_trust_anchor` is the only way to mint a new root over an existing one.
- **Need:** an application's local run signs developers in through a real browser. A random port and a root minted at every start give a new issuer and an unknown certificate authority on every run, so the browser refuses the first sign-in each time.
- **Root shape:** self-signed, critical basic constraints with path length 0, critical key usage limited to certificate and CRL signing, and critical X.509 name constraints permitting only `localhost`, 127.0.0.1/32 and ::1/128. It is valid for 90 days from creation, with a random serial so a replaced root or a new leaf never repeats an issuer/serial pair. A leaf lasts at most 30 days and never beyond the root. OTP `public_key` encodes all of these; OpenSSL refuses a non-loopback leaf the key signs with a permitted-subtree violation, which the test suite checks.
- **Key handling and refusal:** the key file is written through a temporary file whose mode is 0600 before any content, then renamed; a directory Hellhound creates is 0700. Loading refuses, with a typed error and without writing anything, an anchor that is unreadable, corrupt, incomplete, expired, group- or world-readable, or that is not exactly this profile: the private scalar must derive the root's public key, and the root must be version 3, ECDSA P-256 with SHA-256, self-issued, no longer than 90 days, with exactly these four extensions (basic constraints, key usage, name constraints and subject key identifier), each with the criticality and value minted. A root outside the profile is refused as `AnchorMismatch`, and inspecting it never raises. Silent regeneration would invalidate the trust a developer granted without telling them. Creating, loading and replacing the pair happen while holding a lock in the directory: `hellhound-root.lock`, a directory made with `mkdir`, which exactly one caller can create on a local macOS or Linux file system, so starts in several OS processes or worktrees that share one directory see one complete pair: exactly one creates it and the others load it. A start that cannot take the lock within a few seconds reports `AnchorLocked` instead of breaking it, because a lock left by a killed start cannot be told apart from a slow holder without a race of its own; the developer removes it. Publishing each file by hard link or by non-replacing rename was rejected: it makes each file exclusive but not the pair, and it gives replacement no owner. `mkdir` is used rather than an `O_EXCL` lock file because simplifile, which does the file work, exposes it directly, while its `create_file` checks and then writes, which is not exclusive. Without a file handle, the key is not `fsync`ed before its rename; a power loss can leave an empty or partial key, which the next start refuses as corrupt rather than replacing.
- **Residual risk:** a developer who trusts this root trusts a CA whose private key sits on their disk. The name constraints and path length bound what that key can certify only for clients that enforce a trust anchor's own constraints. OpenSSL is the tested client: it refuses a non-loopback leaf, and the suite checks this. Chrome documents enforcement for roots in its platform trust store, which is untested here; Safari and Firefox are untested. Erlang's `ssl` does not apply a trust anchor's own extensions, as RFC 5280 permits, so an Erlang client relies on its hostname check. This is for local development only, never a deployed environment; documentation says how to trust and remove the root on macOS and Linux, and Hellhound runs no trust-store command and picks no global location.
- **Compatibility:** `TestError` is also `authorize`'s error type, so adding variants would break exhaustive matches in 0.2.2 consumers. `start_provider` keeps its signature and maps every start failure to `ProviderStartFailed`; `start` carries the causes. Without the new options a start keeps a free port and a fresh in-memory root, and nothing is written to disk. Only loopback is served. Verification, custody, configuration and production trust are unchanged: only a configuration that names this root trusts it.
- **Implementation and remaining FFI:** the anchor is Gleam (`hellhound/internal/test_anchor`); the package ships no Erlang source. kryptos generates, stores (PKCS#8) and imports the keys and derives the public point from the private scalar; simplifile does the file work and the lock; gleam_crypto gives serials and key identifiers. Five direct calls on OTP `public_key` remain, each for a gap in kryptos 1.5.0 that 1.6.0 also has. `pkix_sign` mints the root and leaf, as OTP records built from Gleam values, because the kryptos builder signs only self-signed certificates and has no name constraints or custom extension. `pkix_decode_cert` and `pkix_verify` inspect and verify a kept root, because kryptos refuses any certificate with a critical extension it does not recognize, and name constraints must be critical. `pem_decode` and `pem_encode` handle the certificate PEM, because kryptos offers certificate PEM only for certificates it can parse or build. Two kryptos additions would remove all five: issuing a certificate signed by another certificate's key, and name constraints (or a raw custom extension) on the builder, recognized when parsing; the profile check would then run on kryptos's parsed certificate and raw extension bytes.
