# Fix the local issuer's port and keep a loopback-constrained root for a local run

<a id="adr-0024"></a>

- **Decision:** the public local issuer gains `with_port` and `with_trust_anchor(directory)`, and a new `start` that returns a typed `StartError` (`InvalidPort`, `PortInUse`, `TrustAnchorFailed(directory, TrustAnchorError)`, `StartFailed`). With an anchor directory, the first start writes a P-256 root and its key there; later starts load and reuse the root and sign a fresh leaf for `localhost` and 127.0.0.1 per start. `replace_trust_anchor` is the only way to mint a new root over an existing one.
- **Need:** an application's local run signs developers in through a real browser. A random port and a root minted at every start give a new issuer and an unknown certificate authority on every run, so the browser refuses the first sign-in each time.
- **Root shape:** self-signed, critical basic constraints with path length 0, critical key usage limited to certificate and CRL signing, and critical X.509 name constraints permitting only `localhost`, 127.0.0.1/32 and ::1/128. It is valid for 90 days from creation, with a random serial so a replaced root or a new leaf never repeats an issuer/serial pair. A leaf lasts at most 30 days and never beyond the root. OTP `public_key` encodes all of these; OpenSSL refuses a non-loopback leaf the key signs with a permitted-subtree violation, which the test suite checks.
- **Key handling and refusal:** the key file is written through a temporary file whose mode is 0600 before any content, then renamed; a directory Hellhound creates is 0700. Loading refuses, with a typed error and without writing anything, an anchor that is unreadable, corrupt, incomplete, expired, group- or world-readable, or whose key does not sign a root carrying exactly these constraints. Silent regeneration would invalidate the trust a developer granted without telling them.
- **Residual risk:** a developer who trusts this root trusts a CA whose private key sits on their disk. The name constraints and path length bound what that key can certify for clients that enforce trust-anchor constraints (browsers and OpenSSL do); Erlang's `ssl` does not apply a trust anchor's own extensions, as RFC 5280 permits, so an Erlang client relies on its hostname check. This is for local development only, never a deployed environment; documentation says how to trust and remove the root on macOS and Linux, and Hellhound runs no trust-store command and picks no global location.
- **Compatibility:** `TestError` is also `authorize`'s error type, so adding variants would break exhaustive matches in 0.2.2 consumers. `start_provider` keeps its signature and maps every start failure to `ProviderStartFailed`; `start` carries the causes. Without the new options a start keeps a free port and a fresh in-memory root, and nothing is written to disk. Only loopback is served. Verification, custody, configuration and production trust are unchanged: only a configuration that names this root trusts it.
