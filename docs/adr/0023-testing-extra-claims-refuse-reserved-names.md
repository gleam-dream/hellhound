# Script extra testing claims through a checked claim value

<a id="adr-0023"></a>

- **Decision:** the public local issuer accepts, for one subject, a list of opaque `ExtraClaim` values through `with_extra_claims` and `set_extra_claims`. They feed newly issued ID tokens and userinfo, beside the email assertions of ADR 0012. `extra_claim(name, json.Json)` is the only constructor and returns `ReservedClaim(name)` for JWT registered claims, the ID-token protocol claims the provider computes or Hellhound verifies, claim-source indirection and the email claims `EmailClaims` owns.
- **Need:** real providers carry application roles in namespaced custom claims and profile data such as `name`. Without them in the local issuer, a consumer that reads its permission from a verified claim needs a development-only grant path in shipped code to test it.
- **Alternatives:** ADR 0012 rejected a general JSON claim bag because it could override issuer, audience or nonce; the checked constructor removes that authority, so a value of `ExtraClaim` cannot name a reserved claim. A closed value type for strings, string lists and booleans would be narrower but invents a JSON subset beside `gleam/json`, which `assertion.with_claim` already uses. Returning `Result` from the builder would break option pipelines; refusing at `start_provider` would add a variant to the public `TestError`.
- **Compatibility:** additive. No entry leaves tokens and userinfo unchanged; another subject is unaffected; a runtime update changes future evidence only; an empty list removes the entry; a repeated name keeps the last value. Verification, custody, configuration, access tokens and the opaque `VerifiedIdentity` are untouched; consumers read the claims through `decode_claims`, the profile accessors and `decode_userinfo`.
- **Scope:** trusted test-provider scripting, not role mapping or authorization policy. Native public-consumer, behaviour and constructor-negative checks qualify this boundary.
