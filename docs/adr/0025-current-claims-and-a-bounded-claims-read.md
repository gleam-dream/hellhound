# Sessions read current claims, and one read bounds their age

<a id="adr-0025"></a>

- **Decision:** a session has login claims and current claims. The login claims are those of the login ID token; they are stored apart and never replaced. The current claims are those of the stored ID token, which a refresh that returns a verified ID token already replaces. Every session read returns the current claims. `authentication_time`, `acr` and `amr` read the login claims, and every other accessor and `decode_claims` read the current claims. `current_identity(client, session, claims_age)` returns an opaque `Current` only when the current claims were issued within the caller's bound, and renews them with one shared refresh when they were not.
- **Need:** a service keeps people signed in until the refresh token, the idle lifetime or the absolute lifetime ends the session. Hellhound 0.2.3 verified and stored the refreshed ID token, yet every session read returned the login claims, so a role removed at the provider kept working until the next login, up to the absolute lifetime.
- **Supersedes:** only the Continuity clause of [ADR 0005](0005-refresh-uncertainty.md), in one sentence: "missing refreshed ID token preserves identity without a new authentication event". It now reads: a missing refreshed ID token leaves the current claims as they were, and a present one replaces them whole, without a new authentication event. The rest of that clause stands: a present ID token retains the original issuer, subject, audience, authorized party, nonce and authentication time; an omitted refresh token is retained; scope sets stay unchanged. ADR 0005's Decision, lease consequence and access policy are untouched: a refresh whose outcome is unknown still quarantines. One settlement changes, stated below: a 429 is a known refusal and releases the generation.
- **Within ADR 0006:** `current_identity` bounds the age of evidence. It reads no role, maps no claim and decides no permission. The application still decodes its own values, chooses its bound, and decides what the claims permit. `Current` marks that the read was checked, in the same way `VerifiedIdentity` marks that the claims were verified; neither is a grant.
- **Replacement is whole:** a claim missing from the refreshed token is gone, and a missing roles claim means no roles. A record without a readable stored ID token reads the login claims and the login issue time, so the stored record format does not change and 0.2.x and 0.3.0 read the same records in both directions.
- **The bound:** `claims_age(client, duration)` builds a checked `ClaimsAge`. It refuses less than 60 s, and a bound not greater than that client's configured clock tolerance. It takes the client because the tolerance is per client and can be configured up to 300 s; a constructor without the client could only check the 60 s floor, which the owner rejected. The bound is an argument, with no configuration key and no default, because it is application policy and may differ by route. Claims pass when their `iat` is within the bound and not later than now plus the clock tolerance. Past the bound the read refreshes from the current custody revision and checks again: `ClaimsNotRenewed(NotReturned)` when no ID token came back, `ClaimsNotRenewed(IssuedTooLongAgo)` when a just-issued token is already past the bound. Both are FixConfiguration and keep the session: OIDC Core §12.2 makes the ID token optional on refresh, so a provider that omits it is a configuration to fix, and a new login would end the same way once per bound. The attempt that called the provider knows whether it published an ID token, so a token reissued with identical claims is not mistaken for a missing one. `RefreshUnconfirmed` is returned as it is (Recover).
- **Renewal circuit:** the same node starts no renewal from `current_identity` for 60 s, and returns `RefreshNotSent(RenewalPaused)` (RetryLater), after a renewal that `current_identity` dispatched ends with the provider's outcome unknown, with a 429, or with `ClaimsNotRenewed`. After the window one renewal is admitted as a probe and the others stay paused until it reports: an answer closes the circuit, a fault opens it for another 60 s, and a probe that does not report within the refresh wait plus the request timeout plus 1 s is taken as lost. The provider cache process holds this state, per node and per cache incarnation. `access_token` and `refresh` do not consult it. The bound covers sessions quarantined for an unknown provider outcome by a bounded read: the renewals already in flight when the first fault returns, then at most one per node per window. A response rejected for one session quarantines that session whatever the circuit's state. A response rejected for one session, a lost refresher lease and a session found already quarantined do not open the circuit: they say nothing about the provider, and one bad session must not pause the node.
- **An unreadable record is the operator's:** `session_error_action(SessionRecordUnreadable)` is `FixConfiguration`, where it was `Reauthenticate`. This ADR tells callers to `logout` on `Reauthenticate`, and an unknown sealing key makes every record unreadable at once, so the old mapping would delete durable sessions that the right key still opens. The cost: a single damaged record denies that person until an operator removes it or the session expires.
- **Whole replacement fails open for restricting claims:** a claim that restricts and that the provider adds only at interactive login is absent after the first refresh. The migration notes say so; the provider must emit it on refresh too.
- **A 429 keeps the session:** a 429 from the token endpoint settles the reservation as not sent and returns `RefreshRateLimited` (RetryLater), on every refresh path. This changes one quarantine rule of ADR 0005, whose decision stands: possible transmission with an unknown outcome still quarantines, and a 429 is a known outcome, a refusal before the grant is processed, like the RFC 6749 §5.2 refusals that already release the generation. The first version of this ADR rejected the change; the owner reversed that after review, because a 15 min bound makes each active session refresh up to 96 times a day where 0.2.3 refreshed about once per access-token lifetime, so a rate-limited provider would sign out every session it admitted. No `Retry-After` is read: the pause is the circuit's fixed window. `access_token` does not consult the circuit, so an expired session under a 429 sends one refresh per request until the provider answers.
- **Telemetry:** the refresh event gains `claims: Replaced | NotReturned`, `quarantine` (none, outcome unknown, response rejected, refresher lost) and the outcome `rate_limited`. Its record type is public, so this is a breaking change. A new event, `[hellhound, current_identity]`, is emitted once per bounded read with how it ended, because a paused read sends no refresh and `IssuedTooLongAgo` follows a refresh that succeeded: neither was visible in the refresh event, and both are the conditions an operator must see. No event reports the fallback to login claims: the ID token is verified before it is sealed and the record is authenticated, so the branch needs a record written without a token.
- **Consequences:** every consumer reads current claims after a version bump. Past the bound, every role-checked request depends on the provider: an outage that is never reached is RetryLater, a brown-out answered with 5xx or a timeout after send quarantines the sessions in flight and then one per window, and a 429 quarantines none. A provider that never returns an ID token on refresh denies every bounded read past the bound until an operator fixes it. Profile claims may be thinner after a refresh. The bound limits the age of the last issued ID token; whether a removed role disappears depends on the provider re-evaluating claims on refresh.
- **Rejected alternatives:**
  - A wrapper, fork or workaround in the service: the owner ruled that the fix is upstream.
  - UserInfo on each check: a provider call per decision, unsigned, and it disagrees with session reads.
  - Roles from the access token (`hellhound/resource`): that token belongs to the API, and its freshness follows the token's lifetime.
  - Access-token lifetime as the bound: it ties a security property to a provider dashboard setting.
  - Each service writes the renewal sequence: every application rebuilds the same subtle rule (shared refresh, missing ID token, retry-later).
  - Merging refreshed claims into the old ones: it keeps a removed role alive when a provider omits the claim.
  - Opt-in replacement: the default would stay stale.
  - Returning the refreshed identity separately from the session: a second copy that drifts.
  - A configured limit with a default: it breaks valid configurations and puts application policy in configuration.
  - Checking and renewing inside `access_token`, with a throttle: it misses `restore_session` and cached reads, and one failure spends the renewal.
  - `IdentityStale` as an `access_token` error: it withholds a valid token from handlers that read no roles.
  - A client-wide pause after a 429 that `access_token` and `refresh` also obey, timed by `Retry-After`: it needs header plumbing and changes `access_token` for every consumer.
  - A cap on renewals in flight while the circuit is closed: it would bound the first wave against a slow provider, and would deny ordinary requests under a burst.
  - Rejecting a refreshed token with an earlier `iat`: the age re-check already enforces the bound.
  - In-call recovery of an unconfirmed publication: a second unconfirmed result would drop the rotated refresh token.
  - An open `Current` record: it can be forged, so it marks nothing.
  - A stale error carrying claims: it invites using them.
  - A separate `Authentication` type: two reads of the same facts.
  - Removing `session_identity`: it breaks about 50 call sites for a policy one service sets.
  - A stored copy of the current claims, or `acr` and `amr` copied into stored evidence: a duplicate of the stored token, or lost when 0.2.x saves the record again.
  - A recorded failed-renewal state or attempt timestamp: a record format change; `logout` on Reauthenticate and the circuit bound the repeats instead.
  - `Access.identity_change`, a one-shot change event: delivered at most once, so it is lost on a crash or a recovery.
  - A per-read telemetry event: it duplicates the refresh event and fires on every request.
  - Redirect renewal (`prompt=none`): it skips non-GET requests and breaks XHR.
  - Silently keeping old claims when no ID token returns: it defeats the bound.
  - Idle polling from long-lived connections: it defeats the idle timeout.
- **Unresolved:** renewals already in flight when the first fault returns are not bounded. A read that used another request's refresh tells `NotReturned` from `IssuedTooLongAgo` by comparing claims, so a token reissued with identical claims reads as `NotReturned` there; both reasons have the same action, and telling them apart needs the publication recorded in custody for readers that did not dispatch. `invalid_scope` after expiry is still retried per request. One `VerifiedIdentity` type reading two claim sets was contested in review and kept, with the three login-pinned accessors documented.
- **Provenance:** the accepted concept brief for Hellhound 0.3.0 (2026-11-24) and its five review rounds; retained bounded-read, replacement, circuit and test-provider tests, and the reference consumer's permission check.
